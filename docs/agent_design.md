**방식 C(탐색 에이전트) 설계**

작성일: 2026-11-22 · 관련 기능: F05 제한된 코드 탐색 에이전트 · 상태: 구현됨(2026-11-23). 실행기는 `analysis/agent.py`, 프롬프트는 `v0-tools1`

이 문서는 방식 C가 무엇을 읽을 수 있고 어디서 멈추는지를 첫 호출 전에 고정한다. 조회 도구의 구현은 `src/ci_failure_analyzer/analysis/tools.py`, 실행기는 `src/ci_failure_analyzer/analysis/agent.py`다. 방식 A/B는 [분석 방식](./analysis_methods.md), 보고서 형식은 [보고서 형식](./report_spec.md), 채점은 [채점 기준](./grading_spec.md)을 따른다.

**방식 C는 방식 A의 입력에서 출발해, 필요한 코드를 도구로 직접 찾아 읽는다.**

| 항목 | 방식 B | 방식 C |
|---|---|---|
| 처음 받는 자료 | 실행 정보, 실패 테스트, 로그, 규칙이 고른 코드 | 실행 정보, 실패 테스트, 로그 (방식 A와 같음) |
| 코드를 고르는 쪽 | 고정 규칙 | 모델 |
| 모델 호출 | 실행당 1회(재요청 포함 최대 2회) | 실행당 최대 8회 |
| 모델, effort, 보고서 형식, 출력 상한 | `configs/analysis.toml` | B와 같음 |

- 방식 B가 일치에 못 미친 실행은 모두 규칙이 원인 파일을 고르지 못한 사례였다([반복 실행 결과](../outputs/dev_ab_repeat_runs.md)). 방식 C로 보려는 것은 모델이 그 파일을 스스로 찾아 읽으면 차이가 메워지는가다.
- 처음 자료를 방식 A와 같게 둔 것은 B와 C의 차이를 "코드를 누가 고르는가" 하나로 만들기 위해서다.
- 프롬프트(`v0-tools1`)는 A/B의 v0에서 "받은 코드 파일"을 말하는 두 문장을 도구 기준으로 바꾸고 "Tools" 절을 더한 것이다. 나머지 문장은 v0과 같다. 문구와 도구 정의가 들어가므로 프롬프트 해시는 A/B와 다르다. dev 결과를 보기 전에 고정했다.

**도구는 세 개이고, 모두 읽기 전용이다.**

| 도구 | 입력 | 돌려주는 것 | 호출당 상한 |
|---|---|---|---|
| `list_files` | `prefix`(선택) | 스냅샷의 파일 경로와 줄 수 | 500개 |
| `read_file` | `path`, `start_line`·`end_line`(선택) | 줄 번호를 붙인 줄 | 200줄 |
| `search_code` | `query`, `prefix`(선택) | `query`가 들어 있는 줄(경로, 줄 번호, 내용) | 50줄 |

- 줄 번호는 방식 A/B의 입력과 인용 검사가 쓰는 것과 같은 기준(`BundleReader.lines`)이다. 도구가 보여 준 번호를 그대로 인용하면 된다.
- `search_code`는 정규식이 아니라 문자열 그대로 찾는다. 모델이 쓴 패턴을 실행하지 않으려는 것이다. 검색 대상은 코드 스냅샷뿐이다.
- 상한을 넘으면 넘은 양을 결과 끝에 적는다. 모델이 범위를 좁혀 다시 부를 수 있다.
- 잘못된 호출(없는 경로, 틀린 인자, 없는 도구)은 예외가 아니라 오류 결과로 돌려준다.

**읽을 수 있는 것은 해당 실행의 입력 묶음뿐이다.**

| 자료 | `list_files` | `read_file` | `search_code` |
|---|---|---|---|
| 코드 스냅샷(CI가 체크아웃한 커밋의 파일) | 가능 | 가능 | 가능 |
| `job.log`, `reports/junit.xml` | - | 가능 | - |
| 묶음의 나머지 파일(`run.json`, `manifest.json` 등) | 불가 | 불가 | 불가 |
| 묶음 밖의 모든 경로(정답, 채점 기록, 다른 사례, 서비스 코드) | 불가 | 불가 | 불가 |
| 저장소 이력, 이후 커밋, 외부 네트워크 | 도구 없음 | 도구 없음 | 도구 없음 |

- 도구는 파일 시스템을 직접 열지 않는다. 경로는 스냅샷 아카이브에 든 일반 파일의 이름과 글자 그대로 같은지만 본다. 그래서 `..`, 절대 경로, 드라이브 문자는 "스냅샷에 없는 이름"으로 거부된다.
- 스냅샷 아카이브는 디스크에 풀지 않고 메모리로 읽는다. 아카이브 안의 심볼릭 링크와 하드 링크는 파일로 치지 않는다.
- `run.json`과 묶음의 `manifest.json`을 막은 것은 브랜치 이름이 들어 있기 때문이다. 평가 사례의 브랜치 이름은 심어 둔 결함을 설명한다. 로그에 나오는 브랜치 이름은 A/B와 같이 `<branch>`로 가려진다.
- 스냅샷에는 `.git` 폴더가 없다. 커밋 메시지와 수정 커밋은 어느 경로로도 읽을 수 없다.
- 이 제한은 `tests/test_tools.py`로 확인한다. 경로 조작 13가지, 묶음 옆에 실제로 있는 파일, 링크 항목, 도구 모듈이 파일을 직접 열지 않는다는 점을 본다.

**실행당 한도는 코드로 강제한다.**

| 항목 | 한도 | 넘으면 |
|---|---|---|
| 도구 호출 | 12회. 오류로 끝난 호출도 센다 | 이후 호출을 거부하고 보고서를 쓰라고 알린다 |
| 모델 호출 | 8회. 도구를 쓸 수 있는 호출은 6번째까지다 | 7번째 호출은 도구 없이 보고서만 받고, 8번째는 검사 실패 뒤의 재요청에만 쓴다 |
| 비용 | 0.60달러 | 다음 호출과 그 뒤의 보고서 호출까지 예상 비용을 더해 넘으면 도구 없이 보고서만 받는다 |
| 호출당 출력 | 8,000 토큰 | 잘리면 `truncated`로 기록한다(A/B와 같음) |

- 모델은 한 번의 응답에서 도구를 여러 개 부를 수 있다. 각각을 도구 호출 1회로 센다.
- 도구 결과를 돌려줄 때마다 남은 도구 호출 수와 남은 차례를 한 줄로 알린다. 한도에 닿으면 그 줄 대신 "도구를 더 부르지 말고 보고서를 내라"는 문장을 붙이고, 그 호출은 도구 목록은 그대로 둔 채 도구 선택을 끈다(`tool_choice: none`).
- 모델 호출 2회를 남겨 두는 것은 2026-11-23에 구현하며 정했다. 마지막 호출에서 받은 보고서가 검사에 실패하면 고칠 기회가 없어지기 때문이다.
- 비용 한도는 예상으로 판단한다. 다음 호출의 입력은 직전 호출의 입력·출력 토큰에 새로 붙는 글을 더해 어림하고, 출력은 3,000 토큰으로 본다. 예상이므로 실제 비용이 한도를 조금 넘을 수 있다. 실행별 실제 비용은 실행 기록에 남는다.
- 모든 모델 호출은 지금처럼 사용량 장부에 먼저 예약하고, 끝난 뒤 기록한다. 전체 상한(85달러)은 A/B와 같은 코드가 지킨다.
- 비용 어림: 호출마다 로그(약 1만 4천 토큰)와 그때까지의 대화가 입력으로 다시 들어간다. 8회를 다 쓰면 입력 약 13만 토큰, 약 0.59달러다. 3~5회에 끝나면 0.25~0.40달러로 본다. 실측은 D7의 첫 실행에서 한다.

**실행은 다음 중 하나로 끝난다.**

| 끝나는 경우 | 처리 | 상태 |
|---|---|---|
| 모델이 도구 없이 보고서를 냄 | 형식 검사와 인용 검사. 통과하면 저장 | `ok` |
| 검사에 실패함 | 문제 목록을 알려 1회만 다시 요청(도구 없이). 또 실패하면 중단 | `check_failed` |
| 한도에 닿음 | 도구 없이 보고서를 요청. 그 보고서를 같은 방법으로 검사 | 검사 결과에 따름. 한도에 닿았다는 사실을 따로 기록 |
| 응답이 잘리거나 모델이 거부함 | 다시 요청하지 않음 | `truncated`, `refused` |

- 한도에 닿아 낸 보고서도 정상 결과로 채점한다. 다만 한도에 닿은 실행의 수를 결과표에 따로 적는다.
- JUnit XML이 없는 입력은 A/B처럼 모델을 호출하지 않고 `out_of_scope`로 끝낸다.

**인용 검사는 "모델이 실제로 본 줄"까지 확인한다.**

- 로그와 JUnit 근거는 A/B와 같은 검사다.
- 코드 근거는 도구 결과로 보여 준 줄이어야 한다. `ToolSession`이 파일별로 보여 준 줄 번호를 기록하고, 인용한 범위에 보여 주지 않은 줄이 하나라도 있으면 `not_in_context` 문제로 돌려준다. 읽지 않은 줄을 짐작으로 인용하는 것을 막으려는 것이다. `read_file`이 보여 준 줄과 `search_code`가 찾아 보여 준 줄이 모두 해당한다.
- 근거가 주장을 뒷받침하는지는 여전히 사람이 본다([근거 표본 점검](../outputs/dev_evidence_check.md)).

**실행 기록에 더 남기는 것**

| 필드 | 내용 |
|---|---|
| `tool_call_count`, `refused_tool_calls` | 도구 호출 수, 한도 뒤에 거부한 수 |
| `tool_calls` | 호출마다 도구 이름, 인자, 오류 여부, 결과 글자 수 |
| `seen_files` | 도구로 본 파일과 줄 범위 |
| `limit_reached` | 닿은 한도(`tool_calls`, `model_calls`, `cost`) 또는 없음 |
| `attempts[].kind` | 모델 호출마다 `explore`(도구를 부른 응답) 또는 `report`(보고서로 검사한 응답) |

- 평가 실행기는 여기서 코드로 판정한다. 원인 파일을 읽었는지(정답의 파일이 `seen_files`에 있는지), 원인 줄을 보았는지, 한도에 닿았는지다. "첫 응답 검사 통과"는 방식 C에서는 첫 보고서 응답을 기준으로 한다.

**첫 호출로 확인할 것 (2026-11-23)**

- 도구 사용과 보고서 스키마 강제(구조화 출력)를 한 호출에서 함께 쓸 수 있는가. 안 되면 탐색이 끝난 뒤 도구 없이 보고서만 받는 호출을 따로 둔다. 그 호출도 모델 호출 8회에 포함한다.
- 입력 캐시를 쓸지. 쓰면 반복해서 들어가는 로그의 비용이 줄지만 A/B와 비용을 비교하는 기준이 달라진다. 실측한 뒤 정한다.
- 평가 실행기는 방식마다 그 방식의 현재 프롬프트 해시로 실행을 고르도록 고쳤다.

**이 문서에서 내가 정한 것**

- **처음 자료를 방식 A와 같게 했다.** B의 자료에서 출발하면 더 적은 호출로 끝나겠지만, 규칙의 선택과 모델의 선택이 섞여 무엇이 효과를 냈는지 가를 수 없다.
- **두 버전 사이의 변경 내역을 보는 도구는 넣지 않았다.** 프로젝트 계획서의 도구 목록에는 있지만, 입력 묶음에는 스냅샷이 하나뿐이고 이전 버전을 주면 무엇이 바뀌었는지가 곧 정답에 가까워진다. 방식 C의 효과를 본 뒤 필요하면 별도 방식으로 다룬다.
- **검색은 문자열 일치만 지원한다.** 정규식이 필요한 사례가 dev에서 나오면 사유와 날짜를 적고 추가한다.
- **`read_file`의 상한을 200줄로 잡았다.** 방식 B의 파일당 400줄보다 작다. 12회를 다 쓰면 최대 2,400줄이다.
- **오류로 끝난 도구 호출도 한도에 센다.** 틀린 인자로 한도 없이 반복하는 것을 막는다.
- **dev 결과를 보고 한도나 도구를 고치면 이 문서에 날짜와 사유를 남긴다.** holdout 실행 전에 고정한다.
