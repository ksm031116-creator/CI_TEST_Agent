**채점 기준**

작성일: 2026-11-21 · 기준 버전: 1 · 관련 기능: F03 평가·재분석 실행기

분석 보고서가 정답의 원인을 맞혔는지 판정하는 기준이다. 정답 형식은 [평가 사례·정답 형식](./eval_case_spec.md), 보고서 형식은 [분석 보고서 형식](./report_spec.md)을 따른다. 계산은 `src/ci_failure_analyzer/evaluation/grading.py`와 `scripts/evaluate.py`가 한다.

**코드가 판정하는 것과 사람이 판정하는 것을 나눈다.**

| 항목 | 판정 | 방법 |
|---|---|---|
| 결론 유형 허용 | 코드 | 보고서의 `conclusion`이 정답의 `acceptable_conclusions`에 있는가. `out_of_scope`는 사유 코드도 같아야 한다 |
| 위치 | 코드 | 1순위 후보의 `location`을 정답의 원인 파일·줄과 비교 |
| 첫 응답 검사 통과 | 코드 | 첫 응답이 끝까지 생성되고 형식·인용 검사를 통과했는가 |
| 확신 high 오답 | 코드 | 확신 `high`인 후보 중 정답 후보가 아닌 것이 있는가. 정답 후보가 무엇인지는 채점 기록에서 가져온다 |
| 원인 일치 | 사람 | 아래 기준으로 일치·부분·불일치 중 하나를 정한다 |

- **1순위 후보**는 확신도가 가장 높은 후보다. 확신도가 같으면 먼저 적힌 후보다.
- **위치**는 네 값 중 하나다. `줄`은 같은 파일에서 정답 줄과 2줄 이내, `파일`은 같은 파일의 다른 줄, `다른 파일`, `없음`(위치를 적지 않음). 정답에 원인 파일이 없는 사례와 범위 밖 사례는 집계에서 뺀다.
- 위치가 얼마나 정확한지는 원인 일치 판정에 쓰지 않는다. 방식 A는 코드를 받지 않아 위치를 적지 못하는 경우가 많기 때문이다. 다만 위치를 결함의 반대쪽(예: 코드 결함인데 테스트 파일)에 적었으면 `wrong_side` 사유가 된다.

**원인 일치는 세 값 중 하나로 판정한다.**

| 판정 | 조건 |
|---|---|
| 일치 (`match`) | 1순위 후보가 정답 후보와 **같은 대상**의 **같은 잘못**을 말하고, 결론 유형이 허용 범위다 |
| 부분 (`partial`) | 정답 후보가 보고서의 후보 안에 있지만 아래 사유 중 하나 이상에 해당한다 |
| 불일치 (`mismatch`) | 정답 후보가 어느 후보에도 없다. 보고서를 내지 못한 실행도 불일치다 |

- **같은 대상**은 정답의 `accepted_candidates`가 가리키는 함수, 설정값, fixture, 외부 데이터 파일이다. 파일 이름이나 줄 번호까지 맞을 필요는 없다.
- **같은 잘못**은 그 대상이 어떻게 틀렸는지다. 예: "경계에서 `>`로 비교한다", "기본값이 20이다", "면세 표시가 빠졌다".
- 후보는 요약(`summary`)과 추론(`reasoning`)을 함께 읽고 판정한다. 추론에만 나온 설명도 그 후보의 내용으로 본다.
- 대상이 다르면 잘못을 비슷하게 말해도 정답 후보가 아니다. 예: 정답이 `Product`의 기본값인데 "로더가 기본값을 잘못 넣는다"고 함.
- 정답이 확인 방법을 요구하는 사례(`accepted_candidates`에 "확인 방법으로 …를 제시해야 함")는 보고서의 `verification_steps`에 그 방법이 있어야 일치다. 없으면 `unspecified` 사유의 부분이다.
- 정답의 `incorrect_conclusions`에 있는 설명은 정답 후보로 치지 않는다.

**부분 판정에는 사유를 하나 이상 적는다.**

| 사유 | 뜻 |
|---|---|
| `not_top` | 정답 후보가 있지만 1순위가 아니다 |
| `unspecified` | 대상이나 잘못을 특정하지 못했다. 서로 다른 대상을 "또는"으로 묶은 후보, 영역만 짚은 후보("상한 검사 쪽 문제"), 대상은 맞지만 잘못을 다르게 말한 후보가 해당한다 |
| `wrong_side` | 같은 사실을 짚었지만 결함의 위치를 반대쪽에 두었다. 예: 설정값이 바뀐 사례에서 테스트의 수량이 잘못이라고 함 |
| `withheld` | 결론 유형이 허용 범위 밖이다. 대개 정답이 `cause_candidate`만 허용하는데 보고서가 `insufficient_evidence`로 낸 경우다 |

- 1순위 후보가 정답과 같고 사유가 `withheld` 하나뿐인 실행은 **"맞는 추정 + 보류"**로 따로 센다. 판정은 부분이다.
- `not_top`은 정답 후보가 1순위가 아닐 때, `withheld`는 결론 유형이 허용 범위 밖일 때 반드시 적는다. 평가 실행기가 이 두 가지를 보고서와 대조해 어긋난 기록을 거부한다.
- "또는"으로 묶은 대안이 모두 같은 대상의 같은 잘못을 달리 표현한 것이면 `unspecified`가 아니다.

**판정 예시 (dev 사례)**

| 사례 | 보고서의 1순위 후보 | 판정 | 이유 |
|---|---|---|---|
| case-009 B | `place_order`의 상한 검사가 `len(items)`를 센다 | 일치 | 대상과 잘못이 정답과 같다 |
| case-002 B | 기본 설정의 기준 수량이 20이라 10개 주문에 할인이 없다 | 일치 | 위치는 적지 않았지만 대상(설정 기본값)과 잘못(값 20)이 같다 |
| case-008 A (1회차) | `line_subtotal`이 경계에서 `>`로 비교한다. 결론은 판단 보류 | 부분 (`withheld`) | 추정은 맞지만 정답은 `cause_candidate`만 허용한다 |
| case-009 A | 상한 검사보다 예약이 먼저이거나, 검사가 없거나 잘못되었다 | 부분 (`unspecified`) | 영역만 짚었고 잘못을 특정하지 못했다 |
| case-002 A (1회차) | 테스트의 수량 10이 기준 수량 20보다 작다. 위치는 테스트 파일 | 부분 (`wrong_side`) | 기준 수량 20이라는 사실은 짚었지만 위치를 테스트 쪽에 두었다 |
| case-010 B (1회차) | `Product`의 기본값이 False이거나 `Catalog`가 값을 바꾼다 | 부분 (`unspecified`) | 앞쪽이 정답이지만 서로 다른 대상을 "또는"으로 묶었다 |
| case-003 A (1회차) | 1순위는 롤백 누락, 2순위(낮은 확신)가 `Inventory`의 해제 구현 오류 | 부분 (`not_top`, `unspecified`, `withheld`) | 정답 후보가 2순위에 영역 수준으로만 있고 결론도 보류다 |
| case-003 A (2회차) | 롤백 누락 하나뿐 | 불일치 | 정답이 오답으로 정한 설명이고, 정답 후보가 없다 |
| case-010 A | 외부 데이터의 과세 표시. 2순위는 로더나 fixture의 해석 오류 | 불일치 | `Product`의 기본값을 든 후보가 없다 |

**코드만으로 판정이 끝나는 실행은 채점 기록을 만들지 않는다.**

- 보고서가 `out_of_scope`이거나 정답이 `out_of_scope`만 허용하면, 결론과 사유 코드가 정답과 같을 때 일치, 아니면 불일치다.
- 보고서를 내지 못한 실행(검사 실패, 잘린 응답, 거부)은 불일치다.

**채점 기록은 실행마다 `evals/gradings/<실행 ID>.json` 하나다.**

| 필드 | 내용 | 채우는 쪽 |
|---|---|---|
| `spec_version` | 이 문서의 기준 버전 | 코드 |
| `run_id`, `case_id`, `method` | 채점 대상 실행 | 코드 |
| `report_sha256` | 채점한 `report.json`의 해시. 보고서가 바뀌면 기록을 쓸 수 없다 | 코드 |
| `conclusion`, `top_candidate` | 보고서의 결론과 1순위 후보(번호, 확신도, 요약). 실행 폴더가 Git에 없어 기록만 보고도 무엇을 채점했는지 알 수 있게 옮겨 둔다 | 코드 |
| `top_candidate_key` | 1순위 후보가 무엇을 원인으로 지목했는지 나타내는 짧은 이름. 같은 사례에서 같은 설명이면 같은 이름을 쓴다 | 채점자 |
| `verdict` | `match`, `partial`, `mismatch` | 채점자 |
| `matched_candidate` | 정답 후보에 해당하는 후보의 번호(1부터). 없으면 `null` | 채점자 |
| `partial_reasons` | 부분 판정의 사유 목록 | 채점자 |
| `rationale` | 판정 이유 한두 문장 | 채점자 |
| `grader`, `graded_on` | 채점자와 날짜 | 채점자 |
| `review` | 사람이 검토했으면 `reviewer`, `date`, `verdict`, `note`. 검토 전에는 `null` | 검토자 |

- `scripts/evaluate.py --split dev --write-stubs`가 코드로 채울 수 있는 필드를 채운 빈 기록을 만든다.
- 검토자의 판정이 있으면 집계는 그 판정을 쓴다. 채점자의 원래 판정은 지우지 않는다.
- 검토되지 않은 판정이 섞인 집계는 "미검토"로 표시하고, 최종 결과로 인용하지 않는다.

**같은 입력을 여러 번 실행한 결과는 실행마다 따로 채점한다.**

- 집계는 실행 단위와 사례 단위를 모두 낸다. 사례 단위에서는 "모든 실행이 일치", "일치가 과반", "판정·결론 유형·1순위 후보가 실행마다 같음"을 센다.
- 1순위 후보가 실행마다 같은지는 `top_candidate_key`가 같은지로 본다.
- 최종 평가에서 사례의 판정을 한 값으로 정하는 규칙(과반, 최저 등)은 아직 정하지 않았다.

**이 기준의 한계**

- 1차 채점자가 분석을 만든 쪽(Claude)이다. 기준을 문서로 고정해도 "같은 대상", "특정했다"의 경계에는 판단이 들어간다. 경계에 있는 판정은 사람 검토로 넘긴다.
- 근거가 주장을 실제로 뒷받침하는지는 이 기준에 없다. 인용한 줄이 존재하는지만 코드로 확인한다.
- 확인 방법과 한계 서술의 품질은 채점하지 않는다. 정답이 확인 방법을 요구하는 사례에서만 있는지 본다.
